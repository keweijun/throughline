# Codex is the only teacher

A course only exists after Codex has prepared it: registering documents, extracting concepts, building the route and checking sources all happen in Codex (ADR 0004). A learner of this app therefore always has Codex installed and signed in, either the CLI or the desktop app. The host runs the `codex` binary it finds through `CODEX_CLI_PATH`, then `PATH`, then the copy bundled with the desktop app.

An earlier draft of this ADR let the interface use any OpenAI-compatible provider as the teacher. That added a provider registry, API key storage and a second model client without serving anyone who could not already run Codex, so it was removed. The host runs every lesson, side question, practice request and preparation through `codex app-server`. The learner chooses only Codex settings: the teacher model, a small model for section preparation and note consolidation, a reasoning effort for each, and fast mode (a Codex service tier, for teacher turns only). The model choices come from the App Server's `model/list`. They are stored per user (`~/.config/guided-learning/settings.json`) and never in a course workspace; `--model`, `--small-model`, `--effort` and `--small-effort` override them for one run.

The runner interface `run(prompt, cwd, emit, cancel)` stays, because tests use fake runners through it. A turn that carries images of the learner's work also passes `images`, a list of local file paths, which `CodexRunner` sends as App Server `localImage` inputs; turns without images do not pass it, so a runner without that parameter still works. Adding another model backend later would mean revisiting this decision, not just adding a class.

## Saved threads for the prompt cache

Each turn used to run in a new ephemeral thread. Codex keys the model's prompt cache by thread and reuses only whole messages, so a teaching turn reused nothing but Codex's own instructions (measured on a real course: 17–30% of ~40K input tokens). A teaching prompt now carries its stable part, the teacher instructions with the route, chapters, learner profile and section context, as `instructions`, which `CodexRunner` sends as the thread's developer instructions; the rest goes in the turn's input. Teaching turns run in saved threads kept per course folder, model and service tier and reverted after every turn, so each turn still sees no history, and turns in a section reuse the cached instructions (about 70% of the input). The prompt is a `str` subclass whose text is the whole prompt, so the runner interface and fake runners stay as they are.

This moves source text from the user message to a developer message. We replayed nine real turns of a course (lesson steps, side questions, preparation, practice) both ways and had a judge model compare each pair blind, in both orders: 13 of 18 judgements were ties and the rest minor and split (3 for the new layout, 2 for the old), none major; reply formats and latency were unchanged. Saved threads are files in the learner's Codex home that Codex may list for the course folder; the host deletes them when idle, when the course closes, and after a crash on the next run. The design uses experimental App Server methods (`thread/resume`, `thread/revert`); if `thread/revert` is missing the runner falls back to ephemeral threads.
