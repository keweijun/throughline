# Architecture

Three layers, each depending only on the one below:

```
web/ (Svelte UI, built into guided_learning/web_dist)
   │  HTTP + one SSE stream, loopback only
guided_learning/server/   Host, features, prompts, FastAPI routes
   │  execute(workspace, {op, ...})
guided_learning/*.py      domain operations (also the Codex skill's JSON CLI)
   │
course.sqlite3 + sources/<id>/<revision> + answer_images/   the course workspace (ADR 0001)
```

## Domain operations

`guided_learning/api.py` dispatches `op` requests to `core`, `sources`, `curriculum`, `teaching`, `evidence`, `background`, `streaming`, `branches`, `practice`, `preparation`, `preferences`, `annotations`, `chapter_builds`, `review`, `memory` and `lessons`. Each call is one `BEGIN IMMEDIATE` transaction on the course database. The Codex skill uses these through the `guided-learning` command (`--course <name>` resolves inside the course library, `--workspace` takes any folder); their names and semantics are a stable contract. The ones Codex uses to build courses are documented in `guided_learning/skill/references/`, which `guided-learning setup` copies to `~/.agents/skills/throughline`; the deprecated chat-teaching operations are in `docs/chat-teaching-operations.md`; the rest (`stream.*`, `branch.*`, `practice.*`, `preparation.*`, `chapter_build.*`, `review.*`, `memory.*`, `lesson.*`) are internal to the host. The host calls the same operations and keeps no state of its own besides worker threads.

Curriculum saves (`curriculum.save`, `curriculum.outline`, `curriculum.chapter.save`, and so `chapter_build.complete`) validate the merged model. Every exercise a save sends needs a nonempty `required_concepts` (`invalid_request` otherwise); exercises stored before the rule in concepts the save does not send may lack it. Exercise placement (ADR 0012) is validated only for what a save writes: an exercise whose `required_concepts` include a concept later in the route, or one not in it, is rejected with `exercise_placement` when its concept is among those the request sends (every concept for `curriculum.save`, none for an outline, the chapter's for a chapter save) or when the save creates the violation (a reorder, a moved concept). Violations stored before the rule stay until their chapter is saved again, so courses keep opening and teaching and one chapter can be fixed at a time; `curriculum.check` reports them read-only. Exercise parts split from one homework question carry `part_of` and `other_parts` (`{question, concept_id?}`).

## Host (`guided_learning/server/`)

- `host.py` — `Host` owns one workspace: takes the single-host lease, marks turns left `running` by a crash as `interrupted`, and runs every model turn through `start_turn` / `pause_turn` / `resume_turn`. Each turn attempt runs in its own thread; runner events become `stream.event` operations, and the `EventBus` publishes `delta`, `turn` and `changed` events.
- `features.py` — the four features, each a class with optional `prompt(turn, context)`, `before_start(request)` and `on_complete(turn)`:
  - `Navigation`: stepped lessons (ADR 0009). A section's first lesson is a `lessons` record (`lesson.begin`) whose plan the teacher writes in step 1's reply (it starts as the section title; the section overview's steps, stored as `outline`, apply only when that reply plans nothing); each step is one mainline turn assigned with `lesson.step` before it starts, so it streams, pauses and regenerates like any lesson. A step prompt carries the plan, the step's title and, after step 1, the text of the steps taught so far; the reply ends with `<lesson-step>{"title"?, "remaining": [{title, added}], "check"?: {idea, question, options: [{text, explanation}], correct}}</lesson-step>`, which the interface hides and `lesson.reply` records on completion (and on restart, for a step completed just before a crash): the step's title, the revised plan of the steps still to teach (at most 8 steps in all, no repeated titles; the teacher may add a bridge step, reorder, merge or drop) and the step's check question (2–5 options with an explanation each, shuffled once; the interface adds "I'm not sure"). An invalid or missing block keeps the plan; an invalid check is dropped without losing a valid plan, and the other way round. Continue (`lesson.step` on the next planned step) needs the previous step completed and the lesson's section to be the current position. Pending explanations are asked of every step and resolved by the last one. Choosing an option shows its explanation (and the correct one after a miss) with no model turn; `lesson.answer` records the choice once on the step (`answer: {choice, unsure, correct, interaction_id}`) and as a `check-answer:<turn id>` interaction with `kind: "check_answer"`, never as evidence, and it neither makes a section reviewable nor counts as a review (ADR 0008). A check can be answered until the next step starts; continuing without answering records nothing. When the previous step's check was answered wrongly or with "I'm not sure", the next step's prompt carries the question, the choice and the correct answer and asks it to open with a short repair. Repeated misses on the check's `idea` become a difficulty in course memory (see Course memory). A later request in a section that already has a lesson, including one saved before steps, is a single reply as before. Lesson prompts depend on position in the chapter (chapter overview or bridge; a course saved without chapters is one chapter), chapter recaps (`recap:` turns owned by the chapter through `chapter_id` and anchored to its last section, which teach nothing new; started from the chapter page once any of its sections has a completed lesson, without moving the position), concept previews (including source material the course plan set aside for the section) and exact-revision source views (Markdown text, PDF page PNG, original PDF). It also delivers pending explanations: a mainline lesson in a section with due explanations is asked to give them in full, and they are resolved when that lesson completes.
  - `Questions`: side questions, the `<teaching-decision>` protocol, foundation supplements, return to the mainline.
  - `Practice`: exercise generation (after a single-reply lesson or a stepped lesson's last step), hints/steps/solutions/assessment, asks, deferral, skipping, entering the next section, skipping a chapter and returning to a skipped section. It also generates retrieval questions (ADR 0008): a generate job with `purpose: "review"` asks for one question for a section, and the chapter quiz (`POST /api/chapters/{id}/quiz`) is a job with `purpose: "chapter_quiz"` and `chapter_id`. `practice.job` freezes the earlier exercises it asks again (`earlier`, chosen by `practice.quiz_earlier`), and `practice.complete` writes them as new tasks (`from_task_id`, question and sources copied) followed by the two or three new questions, which may test only the chapter's studied sections that were not skipped (`practice.quiz_sections`); every quiz task has `origin: "chapter_quiz"`, `chapter_id`, `quiz_id`, `tests_concept_ids` and the chapter's last section as its anchor `concept_id`. A quiz task's help and assessment are recorded for the first section it tests. A generated section exercise that uses one of the section's course exercises names it in `exercise` (that exercise's `question`): the teacher's reply gives it, and it must be one of the section's exercises, or `practice.complete` takes the only course exercise on the task's source units; the interface reads the exercise's `part_of` and `other_parts` from the curriculum to show the homework question a part comes from and the sections teaching its other parts (ADR 0012). An `ask` job (`question` instead of `answer`) answers the learner's question about an exercise or one of its parts: `practice.complete` records the question and answer as interactions and appends `{action: "ask", question, feedback}` to the task's history, with no assessment and no evidence, so it never changes whether the exercise is solved (ADR 0011). Exercises are assessed by part (ADR 0011): a generated exercise, review question or new quiz question may carry `parts` (what each part asks, as text or `{label?, text}` with a short label such as "(a)" that the interface shows instead of "Part N"; a quiz question asked again copies the original's), and a task without them is one part. An assessment reply gives one status per part (`correct`, `partly_correct`, `not_yet`, or `not_attempted` for a part the answer did not address; a reply with only `outcome` still assesses a single-part task). `practice.complete` merges them with the earlier statuses (`practice.part_statuses`; an assessment from before parts counts as its one part), so a `not_attempted` part keeps its status, and appends `parts` and `outcome` (`passed` exactly when every part is correct) to the history entry and to `evidence.assess`. Assessment feedback counts as help on later answers only when it marked an addressed part `partly_correct` or `not_yet`. A review task's assessment, and that of a quiz task testing one section, sets `retest_of` to the section's latest independent pass from another session. `practice.skip` (`id`, optional `reason`: `too_easy`, `too_tedious` or `not_relevant`) closes a section exercise (ADR 0011): status `skipped` and `skip_reason`, with no evidence, outcome or deferral; review and quiz questions are refused (`invalid_action`). It sets `skipped_at`; once two exercises are skipped with the same reason it calls `memory.suggest_from_skips`, and the result carries any new `suggested` preference. Like Do later it cancels a request still running for the exercise. A skipped exercise is never asked again by a chapter quiz nor listed among a recap's deferred exercises; answering it anyway records an attempt as usual and reopens it. An answer may attach images of handwritten work: `save_image` stores each in the workspace's `answer_images/` under its SHA-256 and type, and the assess job, its answer interaction and the task history entry list them by name in `images`. Each feature may name local image files for a turn (`images(turn)`); the host passes them to the runner as `run(prompt, cwd, emit, cancel, images=[paths])`, only when there are any, and `CodexRunner` sends them as `localImage` inputs after the prompt text.
  - `Preparation`: idle-only preparation of the next section; foreground requests pause it.
  - `Memory`: course memory (ADR 0010); see below.
- `builds.py` — `ChapterBuilds` builds an outlined chapter in the app (ADR 0004): a `build` turn on the teacher model whose prompt (`prompts.chapter_build`) carries the outline, learner profile, built route, the text of source units no built chapter maps yet (about 60,000 characters at most, starting after the previous chapter's material) and `waiting_parts`: homework parts that built chapters left for a later one (`other_parts` without `concept_id` not yet mapped), with their unit's text, since their unit is already mapped. The reply is JSON concepts and coverage; `chapter_build.complete` saves it through `curriculum.chapter.save` in one transaction, or discards it when the chapter was built elsewhere meanwhile. A rejected reply (malformed JSON or a validation error) is retried once with the error and the previous reply in the prompt (`chapter_build.reject`), then recorded as failed. Requests come from `POST /api/chapters/{id}/build` and, once per chapter, from the learner studying the last built chapter when the next one is outlined but unbuilt. Records live in the `chapter_builds` namespace, one per chapter: `queued`, `building`, `failed` or `done`; `chapter_build.list` reads a `building` record whose turn no longer runs (after a restart) as `interrupted`, which the learner can build again.
- `review.py` — `Review`: the spaced review schedule read through `review.schedule` (ADR 0008), starting a review (a `purpose: "review"` practice job for a due section) and "Not now" (`review.postpone`). Its `clock` is replaceable in tests.
- `prompts.py` — every instruction sent to a model. Changing wording here changes teaching behavior.
- `app.py` — the FastAPI routes, the loopback Host/Origin guard, the 1 MiB body limit, and static files. `Courses` holds the course library root and the one `Host` currently open; switching courses closes the old host (pausing its turns and releasing its lease) before opening the next. Routes reach the open course through `ActiveHost`, so they do not track switches, and the SSE `EventBus` is shared across switches. A watcher thread polls a read-only fingerprint of each course's `course`, `sources` and `curriculum` records (`library.fingerprint`) and publishes `changed` with scope `library`, plus scope `state` when the open course changed, so edits Codex makes from outside reach open tabs.
- `guided_learning/library.py` lists library courses read-only through operations; `guided_learning/commands.py` implements `setup`, `open`, `stop` and `courses`. `setup` installs the skill, writes the library's `AGENTS.md` (only replacing one it wrote itself), moves courses from earlier default locations, adds a launcher and prints the welcome guide. `open` starts `guided_learning.web --record` detached and reuses it while `.throughline/host.json` in the library points at a live host.

Rules the host enforces: one running mainline lesson at a time; side questions run alongside it unless the learner pauses it; preparation starts only when nothing else runs; memory consolidation runs alongside the learner's turns; a chapter build starts when no learner turn runs, runs alongside preparation, is never paused for the learner, and only one runs at a time; partial text never becomes an interaction or evidence.

## Course memory (`guided_learning/memory.py`, `Memory` feature)

Entries live in the `memory` namespace: `{id, kind, text, status, concept_id, interaction_ids, created_at, updated_at}` with `kind` `preference` (`suggested` until the learner confirms it, then `confirmed`), `taught_term` (`active`) or `difficulty` (`active`, then `cleared`). `stream.start` freezes `memory.prompt` into every prompt snapshot except chapter builds and consolidations as `course_memory`: confirmed preferences, taught terms with their section, and active difficulties with their IDs; suggested, cleared and deleted entries stay out, and learner annotations never enter (ADR 0005). Memory is never evidence.

Check answers keep difficulties up to date without a model turn (ADR 0009, 0010): after `lesson.answer` records an answer, it calls `memory.from_check` (a function, not an operation), which looks at every recorded check answer on the same idea, which means the same `idea_key` (the check's `idea` text after NFKC normalization and case folding, with punctuation and spacing collapsed; the step prompt asks the teacher to name an idea the same way each time and to reuse a difficulty's text when a check tests it). A correct answer clears each active difficulty on the idea (its text has the key, or it cites a check answer on the idea, so a reworded or teacher-noted one clears too), with `cleared_by` the answer's interaction. A miss (wrong or "I'm not sure") is added to such a difficulty's `interaction_ids`; otherwise, once two misses since the latest correct answer on the idea are cited by no difficulty, it creates `check:check-answer:<turn id>` with the check's idea as text, the section of the latest miss and those misses as `interaction_ids`. A deleted difficulty's misses are cited by its tombstone, so it comes back only from two new ones. A correct exercise answer still clears a difficulty through the teacher's memory note.

Lesson and side-question turns end with a `<course-memory>{"entries":[{kind, text, interaction_ids?}], "cleared":[difficulty ids]}</course-memory>` note; practice help and assessment put the same object in a `memory` field of their JSON. On completion the `Memory` feature (last in the feature order, so practice has recorded its interactions) passes it to `memory.note`, which cites the turn's own interactions (`stream-user:`/`stream:`, or `practice-question:`/`practice-answer:`/`practice-feedback:`) plus any existing ones the note names, records each turn's note once (`memory_notes`), skips unknown kinds, merges an entry into a live one of the same kind and text, and refuses one when a deleted entry of that kind cites any of the same interactions. The interface strips the note from displayed text; `Questions` reads `<teaching-decision>` with the note removed. Operations: `memory.view` (live entries: without deleted, merged or pruned ones), `memory.save` (`{id, text}` edits an entry; a new `id` with `kind` and `concept_id` adds one), `memory.confirm` (a suggested preference), `memory.delete` (final: leaves a `deleted` tombstone), `memory.note`, `memory.prompt`. A repeated skip reason suggests a preference without a model turn (ADR 0011): `memory.suggest_from_skips` writes `skip:<reason>` with fixed wording per reason in the course teaching language, `interaction_ids` empty, `skip_ids` (the skipped exercises, since a skip has no interaction) and `skip_reason`. It does nothing while fewer than two exercises are skipped with that reason, and nothing new when a preference with that `skip_reason` or the same text is suggested, confirmed or deleted; a live one gains the new skip in `skip_ids`.

Entering another section (`Practice._enter`: next section, skipping a chapter, a skipped section) starts one `consolidation` turn for the section left, id `consolidation-<section>`, so each section is consolidated once; with no live entries none starts. It runs on the small model with its own prompt (`prompts.memory_consolidation`: the live entries with IDs, kinds, statuses and sections), records no interaction and pauses nothing. The reply is JSON `{"merge":[{into, entries}], "prune":[{id, reason}]}`, which `memory.consolidate` applies once per turn and refuses whole (`invalid_consolidation`, memory unchanged) unless every change names a live entry at most once, merges only entries of the same kind and status (so a suggested preference never merges with a confirmed one), and prunes no confirmed preference; any other field, such as entries to add, is refused too. A merge keeps the kept entry's text and adds the others' interactions and skips; the others become `merged` (`merged_into`), pruned ones `pruned` (`pruned_reason`), each with `consolidated_by`. Deleted entries are never touched. `memory.consolidations` lists the records (`memory_consolidations`: turn, section, merges and prunes). A failed or refused turn changes nothing and is not retried.

## Teacher (`guided_learning/codex.py`, `server/settings.py`)

`CodexRunner` drives `codex app-server`. `TeacherSettings` keeps the teacher model and effort, small model and effort, and service tier (fast mode) per user and builds a runner for each turn, so a change in Teacher settings applies to the next request. Preparation and memory consolidation turns use the small model and effort (each falling back to the teacher's) at the default speed; chapter builds use the teacher model; `background.claim` names the small model in its handoff. `list_models` asks `codex app-server` for `model/list`, following `nextCursor`, and drops hidden models. See ADR 0002.

## HTTP API

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/state` | Course, position, curriculum (with chapters), session, pending explanations, turns, stepped lessons (`lessons`), questions, practice, preparation, settings, annotations, course memory, skipped sections, chapter builds, review (schedule, review questions and their requests; `practice` leaves those out); 409 `no_course` before a course is open |
| GET | `/api/library` | Library root, open course and a summary of each course |
| POST | `/api/library/open` | Open a library course by name (publishes `changed` with scope `course`) |
| POST | `/api/shutdown` | Stop a host started by `guided-learning open` |
| PUT | `/api/preferences` | Save the course interface/teaching language and invalidate stale preparation |
| GET | `/api/events` | SSE: `delta`, `turn`, `changed` |
| POST | `/api/lessons` | Start a mainline lesson (enters the first concept if there is no position): a section's first lesson starts as step 1 of a stepped lesson whose id is the turn id; later ones are single replies |
| POST | `/api/lessons/{id}/steps` | Continue: teach the next planned step (`id` in the body is the turn id); 409 `step_unfinished` until the previous step completes, `lesson_finished` when no step is left, `stale_position` outside the lesson's section, `active_turn` while another lesson is written |
| POST | `/api/lessons/{id}/steps/{turn_id}/check` | Answer a step's check question with `{choice}`, an option index or `"unsure"`; no model turn. 409 `invalid_choice`, `no_check`, `already_answered` (a different choice than the recorded one; the same choice is idempotent), `check_closed` once the next step has started; 404 `unknown_step` |
| POST | `/api/turns/{id}/pause`, `/resume` | Pause, or regenerate as a new attempt |
| GET | `/api/concepts/{id}/preview` | Overview, prerequisites, sources and set-aside material, without moving the position |
| GET | `/api/sources/{source}/{revision}/{unit}?format=image\|pdf` | Exact source revision; Markdown responses include the whole document for the reader |
| POST | `/api/questions`, `/api/questions/{id}/choice`, `/return` | Side questions and supplements |
| POST | `/api/questions/{id}/replies` | Follow up in the same side question; accepts `id`, `question`, and optional `selection` |
| POST | `/api/practice/generate`, `/api/practice/tasks/{id}/{action}` | Exercises and help; `action` is `hint`, `steps`, `solution`, `assess` (body `answer` and optional `images`: up to six uploaded answer images, with which `answer` may be empty), `ask` (body `question`), `defer` or `skip` (body `reason`, optional) |
| POST | `/api/practice/images` | Upload one image of the learner's work as the raw body (`Content-Type: image/…`, PNG, JPEG, GIF or WebP, up to 25 MiB; JSON bodies stay under 1 MiB); returns `{image}`, its name; 415 for anything else |
| GET | `/api/practice/images/{name}` | An uploaded answer image |
| GET | `/api/review` | The review schedule: due sections (oldest first, at most five a day), counts waiting and upcoming, every reviewable section, review questions |
| POST | `/api/review/start` | Start a review of a due section (`concept_id`): asks for a review question, or returns `task_id` of the one waiting |
| POST | `/api/review/postpone` | "Not now": a due section waits one more day |
| POST | `/api/sections/next` | Enter the next route section |
| POST | `/api/sections/enter` | Study a section skipped with its chapter |
| POST | `/api/chapters/{id}/skip` | Defer the rest of the current chapter and enter the next chapter |
| POST | `/api/chapters/{id}/build` | Build an outlined, unbuilt chapter in the background; 409 `not_buildable` for a built or unknown chapter, 409 `build_busy` while another chapter builds |
| POST | `/api/chapters/{id}/recap` | Chapter recap lesson, owned by the chapter; never moves the position. 409 `not_studied` until a section of the chapter has a completed lesson, `active_turn` while another lesson is written |
| POST | `/api/chapters/{id}/quiz` | Take the chapter quiz: earlier exercises asked again plus new questions; same 409 `not_studied`, and `quiz_open` while a question of an earlier quiz is unanswered |
| POST | `/api/preparation/retry` | Retry failed preparation |
| GET/PUT | `/api/settings` | Teacher model and effort, small model and effort, and service tier |
| GET | `/api/models` | Models the Codex sign-in can use, with their reasoning efforts and service tiers; 502 when Codex cannot list them |
| POST | `/api/annotations` | Save a learner annotation (highlight, note or bookmark); `/api/state` lists them |
| PUT/DELETE | `/api/annotations/{id}` | Edit an annotation's note, or delete it |
| PUT/DELETE | `/api/memory/{id}` | Edit a course memory entry's `text`, or delete it (a dismissed suggestion is deleted too); `/api/state` lists entries under `memory` |
| POST | `/api/memory/{id}/confirm` | Confirm a suggested preference so it enters prompts |
| GET | `/api/health` | Process id and launch id; the cheap liveness probe `guided-learning open` and `stop` use |

The browser cannot call domain operations directly; there is no generic operation passthrough. Domain errors return `{error, code}`: 404 for codes starting `unknown_`, 409 for the rest, 400 for invalid request bodies; anything unexpected is logged and returns 500 with code `internal_error`. Besides the Host/Origin guard, any `/api/` request whose `Sec-Fetch-Site` is present and not `same-origin` or `none` is refused.

`/api/state` reads turns through `stream.summaries`, which drops frozen prompt snapshots inside SQLite; the host's own status checks use its brief form. `session.resume` lists open app side questions under `app_questions`, so Codex can see what the learner asked in the app.

## Interface (`web/`)

`lib/store.svelte.ts` holds one reactive copy of `/api/state`, applies SSE deltas to running turns, and refetches after `changed` events. `lib/markdown.ts` renders sanitized Markdown with KaTeX and turns `[Source id / unit]` citations into source buttons, patching only changed blocks so streaming keeps selections and scroll. Before a course is open, and from **Courses** in the top bar, `Library` lists the courses; opening a course reloads the page so the store starts clean. Every hand-off to Codex is a `CodexLink`: a new Codex chat with a `$throughline` request typed in (`codex://new?prompt=…&path=<library>`), which also copies the request and shows a notice, for the Codex CLI or where the link is not handled. The store keeps the library summary while a course is open (`app.libraryCourse`), so the course's own hand-offs (adding files and reviewing from `RouteRail`, reviewing an unchecked location from `SourceViewer`, building the route from an empty `ConceptPage`) name the course by its folder. Components map to the page: `TopBar`; `Library`; `RouteRail` (sections grouped under collapsible chapters when the course has them); `ChapterPage` (a chapter's sections and their progress, source coverage, `ChapterRecap` (recap lessons) and `ChapterQuiz` (the current quiz with its progress, earlier quizzes), and skip, or `ChapterBuild` for a chapter not built yet: build it in the app, its progress, or the error with a Codex link as fallback; `NextSection` shows the same at the end of the last built chapter); `ConceptPage` (goal, next step derived from the section's lessons and practice, questions saved for the section, `UnitOverview` under "About this section", `Lesson` with `TurnControls` (a step shows its position, title and whether the teacher added it; the latest completed step lists the steps left with Continue, which replaces `Composer` until the lesson's last step), `Composer`, `Practice` with `Exercise` (pasted or chosen answer images upload at once, kept by name in the draft and shown by `AnswerImages`), `NextSection` with the next section's `Preparation`, `EarlierHistory`); `SidePanel` (`Questions` with `QuestionThread`, `SourceViewer` with `SourceList` (grouped by this section, this chapter, and the rest), `PdfReader` and `MarkdownReader`, `Notes` (by section, chapter or course, with Markdown export), and `Memory` (course memory by kind, with edit and delete, and Remember / Don't remember for suggested preferences, which `App` also asks in a banner)); `SelectionAsk` (Highlight, Note and Ask on a selected passage), `CitationPeek`, `SettingsDialog` (course language, appearance and teacher, the top bar's one settings entry), `Shortcuts`, `ReviewPage` (due reviews with Start review and Not now, each review question an `Exercise`, and the empty state; **Review** in the top bar opens it in the reading column). The side panel has no tabs of its own: a single switcher in the top bar (Questions, Source, Notes, Memory) picks its view, and picking the open view, the panel's close button or the view's shortcut closes it. An exercise is open until every part is correct (`solved` and `partStatuses` in `lib/format.ts`) or the learner skips it (`open`); every count of open exercises uses that, and a skipped exercise is left out of the solved-of-total counts too. A multi-part `Exercise` shows each part's status and parts correct out of parts. Items with `chapter_id` (recap turns, quiz questions) belong to the chapter page: `app.lessons` and `app.tasks` leave them out, so no section or route-rail count includes them, and `Notes` groups annotations on them under their chapter; review questions are not in `practice` at all. `PdfReader` uses pdf.js (`lib/pdf.ts`), loaded only when a PDF is first opened; it renders pages near the viewport and a selectable text layer. `lib/highlight.ts` paints asked passages and learner highlights with the CSS Custom Highlight API, so lesson and reader DOM is never modified. The window itself does not scroll: the reading column (route rail and page) scrolls in `#stage` beside the side panel, so its scrollbar ends where the panel begins; `lib/stage.ts` holds the offsets and scrolling that used to go through `window`, and forwards page-scrolling keys to the stage when nothing is focused.

Learner annotations are never part of a prompt snapshot or prompt (ADR 0005).

## Adding behavior

- A new kind of model work: add a feature class (or extend one) in `features.py`, its text in `prompts.py`, a route in `app.py`, and any durable records as domain operations.
- Tests: `tests/test_web*.py` drive `Host` directly or through `support.host_client`; `web/tests/*.spec.ts` drive the built UI against fixture courses in `tests/*_fixture.py`.

Language preferences are domain operations (`preferences.view` / `preferences.save`) in the course workspace. Each stream attempt freezes its language alongside its source snapshot. The host emits a preference change notice so connected interfaces refresh their labels without rewriting saved teaching content. Preparation fingerprints include language.

Side questions have a creation timestamp; older records fall back to the original stream start time. The interface shows newest questions first. `branch.reply` appends an idempotent reply (`id` is the branch ID, `reply_id` identifies the reply, with `question` and optional `selection`) without creating another branch or changing the mainline restore point. Earlier answers must be complete. Each reply is a normal pausable/resumable stream, with completed question/answer history frozen in its prompt snapshot. Follow-ups keep the original supplement and pending-explanation decisions; they do not run the branch decision protocol again.

Practice separates learner answers and teacher feedback visually and renders Markdown/LaTeX in both. Unfinished exercises from other sections are initially collapsed. Hints give one cue; key steps provide a symbolic plan, leaving results to the learner; full solutions remain explicit. **Ask about this** opens a separate box for a question about the exercise; its answer appears in the exercise's history and is never assessed. Assessment considers cumulative learner attempts and accepts correct assisted answers without requiring paraphrasing. Evidence provenance still distinguishes assisted completion from independent work.

If a follow-up was saved before its answer stream could start, the interface retries the same reply ID rather than adding another reply. Failed or interrupted practice assessments show the saved submission and offer to restore it to the editor, including after reload and when earlier feedback exists. Learner answer line breaks are retained; selected display formulas keep display delimiters.
