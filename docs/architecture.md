# Architecture

Three layers, each depending only on the one below:

```
web/ (Svelte UI, built into guided_learning/web_dist)
   │  HTTP + one SSE stream, loopback only
guided_learning/server/   Host, features, prompts, FastAPI routes
   │  execute(workspace, {op, ...})
guided_learning/*.py      domain operations (also the Codex skill's JSON CLI)
   │
course.sqlite3 + sources/<id>/<revision> + answer_images/   the course workspace (ADR 0001)
```

## Domain operations

`guided_learning/api.py` dispatches `op` requests to `core`, `sources`, `curriculum`, `teaching`, `evidence`, `background`, `streaming`, `branches`, `practice`, `preparation`, `preferences`, `annotations`, `chapter_builds`, `review`, `memory`, `lessons` and `widgets`. Each call opens the course database and runs in one transaction: operations in `api.READS` (views, lists and reads) in a deferred, query-only transaction that takes no write lock, the rest in `BEGIN IMMEDIATE`. A read that finds the course needs a migration, or writes after all, is run again as a write. Courses use write-ahead logging with `synchronous=NORMAL` (set on the next operation for a course made before), so reads run beside a writer, including Codex's `guided-learning` processes, and a commit appends to the log instead of creating and deleting a journal file; keep courses on a local disk, as the library already advises. The schema is created only by `course.init`. The Codex skill uses these through the `guided-learning` command (`--course <name>` resolves inside the course library, `--workspace` takes any folder); their names and semantics are a stable contract. The ones Codex uses to build courses are documented in `guided_learning/skill/references/`, which `guided-learning setup` copies to `~/.agents/skills/throughline`; the deprecated chat-teaching operations are in `docs/chat-teaching-operations.md`; the rest (`stream.*`, `branch.*`, `practice.*`, `preparation.*`, `chapter_build.*`, `review.*`, `memory.*`, `lesson.*`) are internal to the host. The host calls the same operations and keeps no state of its own besides worker threads and streamed events not yet stored (a quarter second at most). Within a process, `Store` keeps decoded documents between operations and checks them against the stored bytes on every use, which is far cheaper than decoding large JSON again (issue #68): `Store.shared` returns one decoded document that callers only read (the curriculum model through `curriculum.model`, source revisions), and `Store.digest` lists a projection of every document in a namespace, decoding only documents changed since the last listing (`stream.summaries`, the brief `preparation.view`, the turn and interaction lookups operations make). Operation results are always the caller's own objects.

`sources` reads two kinds of file (ADR 0015): a PDF by page, and any UTF-8 or UTF-16 (with a byte order mark) text file by line. Office documents, EPUB and other binary files are refused; Codex converts them to PDF and registers the PDF with `converted_from`, which the source and its snapshot keep as the original's `{path, revision}` (kept when a later registration omits it).

Curriculum saves (`curriculum.save`, `curriculum.outline`, `curriculum.chapter.save`, and so `chapter_build.complete`) validate the merged model. Every exercise a save sends needs a nonempty `required_concepts` (`invalid_request` otherwise); exercises stored before the rule in concepts the save does not send may lack it. Exercise placement (ADR 0012) is validated only for what a save writes: an exercise whose `required_concepts` include a concept later in the route, or one not in it, is rejected with `exercise_placement` when its concept is among those the request sends (every concept for `curriculum.save`, none for an outline, the chapter's for a chapter save) or when the save creates the violation (a reorder, a moved concept). Violations stored before the rule stay until their chapter is saved again, so courses keep opening and teaching and one chapter can be fixed at a time; `curriculum.check` reports them read-only. Exercise parts split from one homework question carry `part_of` and `other_parts` (`{question, concept_id?}`).

## Host (`guided_learning/server/`)

- `host.py` — `Host` owns one workspace: takes the single-host lease, marks turns left `running` by a crash as `interrupted`, and runs every model turn through `start_turn` / `pause_turn` / `resume_turn`. Each turn attempt runs in its own thread, and the `EventBus` publishes `delta`, `turn` and `changed` events. Runner events are numbered as they arrive; a delta is published at once and buffered, and buffered events are stored with `stream.events` (several events of one attempt, applied in order and written once) at most every `persist_interval` (0.25 s), and at once with a `final`, `complete` or `failed` event. Every operation through `Host.operation` stores buffered events first, so what the host reads, `/api/state` included, holds every delta already published, which keeps the interface's in-order delta merging exact; a crash loses at most the last interval's text, and restart marks the turn `interrupted` with the text stored so far. A write that fails stays buffered and is tried again; when the reply's last event cannot be stored the attempt is marked `failed`. While a host is open it holds an idle database connection (`store.hold`), since SQLite deletes the write-ahead log and its index whenever the last connection closes.
- `features.py` — the four features, each a class with optional `prompt(turn, context)`, `before_start(request)` and `on_complete(turn)`:
  - `Navigation`: stepped lessons (ADR 0009). A section's first lesson is a `lessons` record (`lesson.begin`) whose plan the teacher writes in step 1's reply (it starts as the section title; the section overview's steps, stored as `outline`, apply only when that reply plans nothing); each step is one mainline turn assigned with `lesson.step` before it starts, so it streams, pauses and regenerates like any lesson. A step prompt carries the plan, the step's title and, after step 1, the text of the steps taught so far; the reply ends with `<lesson-step>{"title"?, "remaining": [{title, added}], "check"?: {idea, question, options: [{text, explanation}], correct}}</lesson-step>`, which the interface hides and `lesson.reply` records on completion (and on restart, for a step completed just before a crash): the step's title, the revised plan of the steps still to teach (at most 8 steps in all, no repeated titles; the teacher may add a bridge step, reorder, merge or drop) and the step's check question (2–5 options with an explanation each, shuffled once; the interface adds "I'm not sure"). An invalid or missing block keeps the plan; an invalid check is dropped without losing a valid plan, and the other way round. Continue (`lesson.step` on the next planned step) needs the previous step completed and the lesson's section to be the current position. **Prepared step**: when a step completes and the plan has a next step, the host at once starts writing that step on the hidden `prepared_step` channel (`Navigation.prepare`; id `step:<uuid>`, no user interaction recorded, and none recorded on completion), and `lesson.prepare` records it as the lesson's `prepared` turn. Its prompt snapshot carries `lesson_step: {lesson_id, number, missed_check}`, the step it writes and the check miss it repairs (null when the check was unanswered or right), and its prompt is built from that snapshot. It is left out of `/api/state` turns and SSE `turn`/`delta` events, its reply is not recorded, and completion hooks ignore it. Continue reveals it when it is still running or complete, is the next step, matches the repair the last check now calls for and the current language: `lesson.step` with its turn id (and the Continue `id` as `request_id`, so a retried Continue returns it) turns it into a mainline turn in the same transaction, recording the Continue request and, if complete, the reply as interactions; the host then publishes it and, if complete, runs the completion hooks it skipped. Otherwise Continue drops it (stopping it) and writes the step as before. A wrong or "not sure" check answer drops the prepared step and prepares one with the repair at once; a correct answer keeps it. Starting or regenerating any mainline lesson, pausing a mainline turn (including a side question asked with pause, or the teacher's `mainline_error`), and entering another section drop it; a prepared step stopped by a restart is never resumed (`invalid_transition`), so Continue writes the step. Nothing is prepared after the last step, outside the current section, or while another lesson is being written. A running prepared step pauses and holds off section preparation like a learner request; a chapter build may run alongside it. Pending explanations are asked of every step and resolved by the last one. Choosing an option shows its explanation (and the correct one after a miss) with no model turn; `lesson.answer` records the choice once on the step (`answer: {choice, unsure, correct, interaction_id}`) and as a `check-answer:<turn id>` interaction with `kind: "check_answer"`, never as evidence, nor as a review answer (ADR 0014). A check can be answered until the next step starts; continuing without answering records nothing. When the previous step's check was answered wrongly or with "I'm not sure", the next step's prompt carries the question, the choice and the correct answer and asks it to open with a short repair. Repeated misses on the check's `idea` become a difficulty in course memory (see Course memory). A later request in a section that already has a lesson, including one saved before steps, is a single reply as before. Lesson prompts depend on position in the chapter (chapter overview or bridge; a course saved without chapters is one chapter), chapter recaps (`recap:` turns owned by the chapter through `chapter_id` and anchored to its last section, which teach nothing new; started from the chapter page once any of its sections has a completed lesson, without moving the position), concept previews (including source material the course plan set aside for the section) and exact-revision source views (a text file's lines, PDF page PNG, original PDF, and the name of the document it was converted from). It also delivers pending explanations: a mainline lesson in a section with due explanations is asked to give them in full, and they are resolved when that lesson completes.
  - `Questions`: side questions, the `<teaching-decision>` protocol, foundation supplements, return to the mainline.
  - `Practice`: exercise generation (after a single-reply lesson or a stepped lesson's last step), hints/steps/solutions/assessment, asks, deferral, skipping, entering the next section, skipping a chapter, jumping to a later section (the sections passed over without a completed lesson, the current one included, are deferred as `route-skip:` like a skipped chapter's `chapter-skip:`) and returning to a skipped section. It also generates retrieval questions (ADR 0014): a generate job with `purpose: "review"` and `set_id` writes the questions of a review set (`practice._review_questions`: each tests sections `review.scope_sections` allows for the set; a recall question is checked like a lesson check question (`lessons._check`, options shuffled once) and dropped when malformed; an apply question may give each part `concept_ids` among the sections it tests; at most `review.MAX_QUESTIONS`; the reply's `note` is kept on the set), stored as tasks with `origin: "review"`, `set_id`, `kind`, `tests_concept_ids` and the first section tested as `concept_id`. The chapter quiz (`POST /api/chapters/{id}/quiz`) is a job with `purpose: "chapter_quiz"` and `chapter_id`. `practice.job` freezes the earlier exercises it asks again (`earlier`, chosen by `practice.quiz_earlier`), and `practice.complete` writes them as new tasks (`from_task_id`, question and sources copied) followed by the two or three new questions, which may test only the chapter's studied sections that were not skipped (`practice.quiz_sections`); every quiz task has `origin: "chapter_quiz"`, `chapter_id`, `quiz_id`, `tests_concept_ids` and the chapter's last section as its anchor `concept_id`. A quiz task's help and assessment are recorded for the first section it tests. A generated section exercise that uses one of the section's course exercises names it in `exercise` (that exercise's `question`): the teacher's reply gives it, and it must be one of the section's exercises, or `practice.complete` takes the only course exercise on the task's source units; the interface reads the exercise's `part_of` and `other_parts` from the curriculum to show the homework question a part comes from and the sections teaching its other parts (ADR 0012). An `ask` job (`question` instead of `answer`) answers the learner's question about an exercise or one of its parts: `practice.complete` records the question and answer as interactions and appends `{action: "ask", question, feedback}` to the task's history, with no assessment and no evidence, so it never changes whether the exercise is solved (ADR 0011). Exercises are assessed by part (ADR 0011): a generated exercise, review question or new quiz question may carry `parts` (what each part asks, as text or `{label?, text}` with a short label such as "(a)" that the interface shows instead of "Part N"; a quiz question asked again copies the original's), and a task without them is one part. An assessment reply gives one status per part (`correct`, `partly_correct`, `not_yet`, or `not_attempted` for a part the answer did not address; a reply with only `outcome` still assesses a single-part task). `practice.complete` merges them with the earlier statuses (`practice.part_statuses`; an assessment from before parts counts as its one part), so a `not_attempted` part keeps its status, and appends `parts` and `outcome` (`passed` exactly when every part is correct) to the history entry and to `evidence.assess`. Assessment feedback counts as help on later answers only when it marked an addressed part `partly_correct` or `not_yet`. A review task's assessment, and that of a quiz task testing one section, sets `retest_of` to the section's latest independent pass from another session. `practice.skip` (`id`, optional `reason`: `too_easy`, `too_tedious` or `not_relevant`) closes a section exercise (ADR 0011): status `skipped` and `skip_reason`, with no evidence, outcome or deferral; review and quiz questions are refused (`invalid_action`). It sets `skipped_at`; once two exercises are skipped with the same reason it calls `memory.suggest_from_skips`, and the result carries any new `suggested` preference. Like Do later it cancels a request still running for the exercise. A skipped exercise is never asked again by a chapter quiz nor listed among a recap's deferred exercises; answering it anyway records an attempt as usual and reopens it. Different exercises (ADR 0011): `Practice.replace` starts a generate job with `replaces`, the section's exercises `practice.replaceable` holds for (`origin: "self_created"`, status `pending`, no history), and an optional `note` (the learner's words, recorded as a `practice-request:` interaction); `practice.complete` writes the new exercises and only then sets each listed exercise still untouched to status `replaced` (`replaced_by`, `replaced_at`), so a failed request replaces nothing and one touched meanwhile is kept. `/api/state` leaves replaced tasks out. The `variant` action (Another like this) is a generate job with `variant_of`, whose reply must be exactly one `self_created` question, stored with `variant_of`; the interface lists a variant right after its exercise (`app.tasks` orders by `created_at`, which generated tasks carry). Both prompts (`prompts.different_exercises`) pass the note, the exercises replaced or copied and those the learner keeps, and hold the section objective; a request with a note asks for a memory note, which may suggest a practice preference citing it. An answer or an `ask` may attach images (`images.py`): `images.save` stores each in the workspace's `answer_images/` under its SHA-256 and type, and the job, its answer or question interaction and the task history entry list them by name in `images`. Side questions and follow-ups (`branch.begin`, `branch.reply`) and learner notes (`annotations.save`) take the same `images`; a side question's are sent with the turn that answers it, a note's never reach the teacher (ADR 0005). Each feature may name local image files for a turn (`images(turn)`); the host passes them to the runner as `run(prompt, cwd, emit, cancel, images=[paths])`, only when there are any, and `CodexRunner` sends them as `localImage` inputs after the prompt text.
  - `Preparation`: idle-only preparation of the next section; foreground requests pause it.
  - `Memory`: course memory (ADR 0010); see below.
- `builds.py` — `ChapterBuilds` builds an outlined chapter in the app (ADR 0004): a `build` turn on the teacher model whose prompt (`prompts.chapter_build`) carries the outline, learner profile, built route, the text of source units no built chapter maps yet (about 60,000 characters at most, starting after the previous chapter's material) and `waiting_parts`: homework parts that built chapters left for a later one (`other_parts` without `concept_id` not yet mapped), with their unit's text, since their unit is already mapped. The reply is JSON concepts and coverage; `chapter_build.complete` saves it through `curriculum.chapter.save` in one transaction, or discards it when the chapter was built elsewhere meanwhile. A rejected reply (malformed JSON or a validation error) is retried once with the error and the previous reply in the prompt (`chapter_build.reject`), then recorded as failed. Requests come from `POST /api/chapters/{id}/build` and, once per chapter, from the learner studying the last built chapter when the next one is outlined but unbuilt. Records live in the `chapter_builds` namespace, one per chapter: `queued`, `building`, `failed` or `done`; `chapter_build.list` reads a `building` record whose turn no longer runs (after a restart) as `interrupted`, which the learner can build again.
- `review.py` — `Review` (ADR 0014): asking for a review set (`review.create`, then a `purpose: "review"` practice job anchored to a section the set may test, or to the section a warm-up comes before), Review for me taking the prepared set (`review.take_prepared`; a prepared set whose writing failed is closed and replaced), closing a set, recall answers (`review.answer`: a `review-answer:` interaction of kind `review_answer` and the task's `answer`, never evidence) and dismissing a warm-up. `prepare` writes the hidden prepared set; the preparation loop calls it when it has nothing to start, nothing is running and the learner has asked for a review in this course before. The domain module `guided_learning/review.py` computes the review context (`review.context`: per studied section, days since last practised, recent misses and set-aside exercises; earlier review and quiz questions with their outcomes), lists sets with their progress (`review.sets`) and the warm-ups on offer (`review.warm_ups`). Its `clock` is replaceable in tests, and `ahead = False` stops the background prepared set.
- `prompts.py` — every instruction sent to a model. Changing wording here changes teaching behavior.
- `app.py` — the FastAPI routes, the loopback Host/Origin guard, the 1 MiB body limit, and static files. `Courses` holds the course library root and the one `Host` currently open; switching courses closes the old host (pausing its turns and releasing its lease) before opening the next. Routes reach the open course through `ActiveHost`, so they do not track switches, and the SSE `EventBus` is shared across switches. A watcher thread polls a read-only fingerprint of each course's `course`, `sources` and `curriculum` records (`library.fingerprint`), reading only courses whose `course.sqlite3` or write-ahead log changed size or modification time since the last poll (`library.stamp`), and publishes `changed` with scope `library`, plus scope `state` when the open course changed, so edits Codex makes from outside reach open tabs.
- `guided_learning/library.py` lists library courses read-only through operations; `guided_learning/commands.py` implements `setup`, `open`, `stop`, `courses` and `doctor` (a readable check of the install, including one tiny turn to a small model to see that Codex answers; its checks live in `guided_learning/checks.py`, which the library uses too). `setup` installs the skill, writes the library's `AGENTS.md` (only replacing one it wrote itself), moves courses from earlier default locations, adds a launcher (on macOS in `/Applications` when writable, else `~/Applications`), starts the host and opens the library in the browser (`--no-open` skips that; a failure to open never fails setup) and prints a short welcome guide. `open` starts `guided_learning.web --record` detached and reuses it while `.throughline/host.json` in the library points at a live host.

Rules the host enforces: one running mainline lesson at a time, plus at most one prepared step; side questions run alongside it unless the learner pauses it; preparation starts only when nothing else runs; memory consolidation runs alongside the learner's turns; a chapter build starts when no learner turn runs, runs alongside preparation, is never paused for the learner, and only one runs at a time; partial text never becomes an interaction or evidence.

## Course memory (`guided_learning/memory.py`, `Memory` feature)

Entries live in the `memory` namespace: `{id, kind, text, status, concept_id, interaction_ids, created_at, updated_at}` with `kind` `preference` (`suggested` until the learner confirms it, then `confirmed`), `taught_term` (`active`) or `difficulty` (`active`, then `cleared`). `stream.start` freezes `memory.prompt` into every prompt snapshot except chapter builds and consolidations as `course_memory`: confirmed preferences, taught terms with their section, and active difficulties with their IDs; suggested, cleared and deleted entries stay out, and learner annotations never enter (ADR 0005). Memory is never evidence.

## Teaching widgets (`guided_learning/widgets.py`, `web/src/lib/widgets.ts`)

ADR 0013. Lessons are Markdown; the interface draws some of it. Basic widgets are always available and described in `prompts.TEACHER`: LaTeX, code fences highlighted by highlight.js, callouts (`> [!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, `[!CAUTION]`) and Mermaid diagrams (```` ```mermaid ````). Add-ons are listed in `widgets.LIBRARY`, each with a summary and subjects for Codex to choose by and a guide for the teacher: `plot` (```` ```plot ```` function graphs, drawn by `web/src/lib/plot.ts`, which parses expressions itself) and `chemistry` (mhchem's `\ce{}` and `\pu{}` in formulas). `widgets.list` returns the library and the course's selection (`course/widgets`, `{ids}`; none when absent), and `widgets.save {ids}` replaces it. `stream.start` freezes the selection into each prompt snapshot except chapter builds and consolidations as `widgets`, and `prompts.instructions` appends the selected add-ons' guides to the stable developer instructions, so they stay cached across a section's turns.

The interface renders every widget in the library whatever the course selected, so deselecting an add-on never breaks a lesson written with it. `lib/widgets.ts` loads highlight.js, Mermaid and mhchem with dynamic imports on first use; drawing is synchronous from caches (Mermaid drawings are cached by theme and source), and when a library or a drawing is ready, or the theme changes, `lib/markdown.ts` renders its mounted Markdown again. A diagram or plot is drawn only once its fence has closed, so a streaming lesson shows the source until then; one that fails shows its source under a short note. Mermaid runs with `securityLevel: "strict"` and its SVG is sanitized again. Learner highlights and citation linking skip `.widget` drawings, as they skip KaTeX. The build replaces Mermaid's optional ELK layout with its default layout (`web/vite.config.ts`).

Check answers keep difficulties up to date without a model turn (ADR 0009, 0010): after `lesson.answer` records an answer, it calls `memory.from_check` (a function, not an operation), which looks at every recorded check answer on the same idea, which means the same `idea_key` (the check's `idea` text after NFKC normalization and case folding, with punctuation and spacing collapsed; the step prompt asks the teacher to name an idea the same way each time and to reuse a difficulty's text when a check tests it). A correct answer clears each active difficulty on the idea (its text has the key, or it cites a check answer on the idea, so a reworded or teacher-noted one clears too), with `cleared_by` the answer's interaction. A miss (wrong or "I'm not sure") is added to such a difficulty's `interaction_ids`; otherwise, once two misses since the latest correct answer on the idea are cited by no difficulty, it creates `check:check-answer:<turn id>` with the check's idea as text, the section of the latest miss and those misses as `interaction_ids`. A deleted difficulty's misses are cited by its tombstone, so it comes back only from two new ones. A correct exercise answer still clears a difficulty through the teacher's memory note.

Lesson and side-question turns end with a `<course-memory>{"entries":[{kind, text, interaction_ids?}], "cleared":[difficulty ids]}</course-memory>` note; practice help and assessment put the same object in a `memory` field of their JSON. On completion the `Memory` feature (last in the feature order, so practice has recorded its interactions) passes it to `memory.note`, which cites the turn's own interactions (`stream-user:`/`stream:`, or `practice-question:`/`practice-answer:`/`practice-feedback:`) plus any existing ones the note names, records each turn's note once (`memory_notes`), skips unknown kinds, merges an entry into a live one of the same kind and text, and refuses one when a deleted entry of that kind cites any of the same interactions. The interface strips the note from displayed text; `Questions` reads `<teaching-decision>` with the note removed. Operations: `memory.view` (live entries: without deleted, merged or pruned ones), `memory.save` (`{id, text}` edits an entry; a new `id` with `kind` and `concept_id` adds one), `memory.confirm` (a suggested preference), `memory.delete` (final: leaves a `deleted` tombstone), `memory.note`, `memory.prompt`, `memory.request` (records what the learner asked to be remembered as a `memory-request:` interaction and a `memory_requests` record whose `turn_id` is `memory-<id>`), `memory.requests`, `memory.answer` (applies the `memory` turn's JSON reply `{reply, remember, forget}` once: `remember` adds confirmed preferences with no section citing the request, `forget` deletes listed preferences; a malformed reply changes no entry and leaves `error` on the request). The `memory` channel is background work on the small model, with its own prompt (`prompts.memory_request`: the message and the live preferences). A repeated skip reason suggests a preference without a model turn (ADR 0011): `memory.suggest_from_skips` writes `skip:<reason>` with fixed wording per reason in the course teaching language, `interaction_ids` empty, `skip_ids` (the skipped exercises, since a skip has no interaction) and `skip_reason`. It does nothing while fewer than two exercises are skipped with that reason, and nothing new when a preference with that `skip_reason` or the same text is suggested, confirmed or deleted; a live one gains the new skip in `skip_ids`.

Entering another section (`Practice._enter`: next section, skipping a chapter, a skipped section) starts one `consolidation` turn for the section left, id `consolidation-<section>`, so each section is consolidated once; with no live entries none starts. It runs on the small model with its own prompt (`prompts.memory_consolidation`: the live entries with IDs, kinds, statuses and sections), records no interaction and pauses nothing. The reply is JSON `{"merge":[{into, entries}], "prune":[{id, reason}]}`, which `memory.consolidate` applies once per turn and refuses whole (`invalid_consolidation`, memory unchanged) unless every change names a live entry at most once, merges only entries of the same kind and status (so a suggested preference never merges with a confirmed one), and prunes no confirmed preference; any other field, such as entries to add, is refused too. A merge keeps the kept entry's text and adds the others' interactions and skips; the others become `merged` (`merged_into`), pruned ones `pruned` (`pruned_reason`), each with `consolidated_by`. Deleted entries are never touched. `memory.consolidations` lists the records (`memory_consolidations`: turn, section, merges and prunes). A failed or refused turn changes nothing and is not retried.

## Teacher (`guided_learning/codex.py`, `server/settings.py`)

`CodexRunner` drives `codex app-server`. `TeacherSettings` keeps the teacher model and effort, small model and effort, and service tier (fast mode) per user and builds a runner for each turn, so a change in Teacher settings applies to the next request. Preparation and memory consolidation turns use the small model and effort (each falling back to the teacher's) at the default speed; chapter builds use the teacher model; `background.claim` names the small model in its handoff. `list_models` asks `codex app-server` for `model/list`, following `nextCursor`, and drops hidden models. See ADR 0002.

A teaching prompt (`prompts.Prompt`, from `Host.build_prompt`) has two parts. Its `instructions` are the teacher instructions and the snapshot parts that stay the same through a section: `route`, `chapters`, `learner_profile`, `language` and `context`. Its `request` is the rest of the snapshot (course memory, branch or lesson step, session, and recent interactions last), the learner's request and the feature instructions. Its text is both parts, so fake runners read it as a string. `CodexRunner` sends the instructions as the thread's `developerInstructions` and the request as the turn's input, in a saved thread lent from `codex.THREADS`: the first turn for a course folder, model and service tier starts one (`ephemeral: false`), each turn is reverted when it completes (`thread/revert`) and the thread archived (`thread/archive`) so idle threads stay out of the learner's Codex session list, and the next turn unarchives and resumes it (`thread/unarchive`, then `thread/resume` with `excludeTurns`). Codex keys the prompt cache by thread and reuses only whole messages, so this lets turns in a section reuse the cached developer instructions: about 70% of a turn's input instead of Codex's own ~30%. A failed, stopped or unreverted turn's thread is deleted rather than lent again; a thread that cannot be resumed is replaced; a Codex without `thread/revert` gets ephemeral threads for the rest of the run. Idle threads are deleted after 15 minutes, beyond three per key, and when the host closes; the first turn in a course folder also deletes the non-ephemeral `guided_learning` threads, archived or not, an earlier run left there. Chapter builds and memory consolidation send plain prompts and run in ephemeral threads.

## Studio (`server/studio.py`, ADR 0016)

Studio is course work as a Codex chat. `Studio` keeps one long-lived `codex app-server` process (`AppServer`), started on first use and again after it exits, with the client name `throughline_studio`, which is also its threads' originator, so the teaching-thread sweep in `codex.py` never touches them. On start it checks that this Codex has `thread/turns/list` and `turn/steer`; without them Studio reports itself unavailable and the hand-offs open a Codex chat instead. Studio threads are saved threads in the library folder (the course folder for a host started on one course), with developer instructions that name the open course, say the app is already open and that attached files are already in the course's `inputs/`. The host keeps no transcript: `studio.json` beside the teacher settings records Full access and each course's thread IDs, newest first, and history is read back with `thread/turns/list`. Every `turn/start` carries the current access: the workspace-write sandbox with the library as the only writable root, no network and approval on request, or with Full access no sandbox and no approvals; on Windows, when `windowsSandbox/readiness` is not `ready`, Studio runs with full access. A message while a turn runs steers it (`turn/steer`). Codex's approvals and `item/tool/requestUserInput` questions on Studio threads wait in `pending` until the learner answers; other requests are refused. Notifications about loaded Studio threads (`thread/`, `turn/`, `item/`, `error`) and rate-limit updates go to the interface as SSE events `{type: "studio", method, params}`, as Codex sends them, plus `studio/request`, `studio/resolved`, `studio/threads` and `studio/closed`. `message_input` builds a message's App Server input: the text with its chips as `text_elements` (UTF-8 byte ranges), then a hand-off's context as its own text input marked `Context from Throughline: `, then `skill`, `mention` and `localImage` items. `activity` reports the course's threads Codex works in or waits on from what the host saw, without starting Codex.

The browser cannot call domain operations directly; there is no generic operation passthrough. Domain errors return `{error, code}`: 404 for codes starting `unknown_`, 409 for the rest, 400 for invalid request bodies; anything unexpected is logged and returns 500 with code `internal_error`. Besides the Host/Origin guard, any `/api/` request whose `Sec-Fetch-Site` is present and not `same-origin` or `none` is refused.

`/api/state` (`server/state.py`) reads turns through `stream.summaries`, which drops frozen prompt snapshots; the host's own status checks use its brief form. It reads preparation through `preparation.view` with `brief: true`, which lists jobs (and `ready`) without their snapshot and material. It sends only the fields the interface reads, so it stays small on large courses; the operations keep every field. Sections keep `id`, `title`, `prerequisites`, `objective`, `goal`, `links` as bare references and `exercises` with their placement (`question`, `part_of`, `other_parts`); coverage entries keep their reference, sections, disposition and verification; `curriculum.version` is a hash of the whole plan, which the section preview follows. Preparation jobs leave out their snapshot and material, the session keeps only `recent_interactions`, and the learner profile is left out. A turn carries one text: `text` is the streamed text, and the final text once complete (no `final_text`, `prompt` or `metrics`); a background turn (preparation, build, consolidation), which no view shows, carries no text, attempts or references. SSE `turn` events carry the same turn. A finished preparation turn publishes `changed` with scope `preparation`, and a finished consolidation scope `memory`, so the interface reloads only that part. `session.resume` lists open app side questions under `app_questions`, so Codex can see what the learner asked in the app. A prompt snapshot's session leaves out `app_questions` and the section context, which `context` already carries. A completed turn's `metrics` keep timings and, from Codex, `usage`: the turn's input, cached input, output and reasoning tokens summed over its model requests.

## Adding behavior

- A new kind of model work: add a feature class (or extend one) in `features.py`, its text in `prompts.py`, a route in `app.py`, and any durable records as domain operations.
- Tests: `tests/test_web*.py` drive `Host` directly or through `support.host_client`; `web/tests/*.spec.ts` drive the built UI against fixture courses in `tests/*_fixture.py`.

Language preferences are domain operations (`preferences.view` / `preferences.save`) in the course workspace. Each stream attempt freezes its language alongside its source snapshot. The host emits a preference change notice so connected interfaces refresh their labels without rewriting saved teaching content. Preparation fingerprints cover only what the section's preparation depends on (its context, the learner profile and the teaching language), so edits elsewhere in the course keep it.

Side questions have a creation timestamp; older records fall back to the original stream start time. The interface lists questions oldest first, so a new one appears just above the box it was asked in. `branch.reply` appends an idempotent reply (`id` is the branch ID, `reply_id` identifies the reply, with `question` and optional `selection`) without creating another branch or changing the mainline restore point. Earlier answers must be complete. Each reply is a normal pausable/resumable stream, with completed question/answer history frozen in its prompt snapshot. Follow-ups keep the original supplement and pending-explanation decisions; they do not run the branch decision protocol again.

Practice separates learner answers and teacher feedback visually and renders Markdown/LaTeX in both. Unfinished exercises from the chapter's other sections are initially collapsed on the current section; those of other chapters are listed only on their chapter page. Hints give one cue; key steps provide a symbolic plan, leaving results to the learner; full solutions remain explicit. **Ask about this** opens a separate box for a question about the exercise; its answer appears in the exercise's history and is never assessed. Assessment considers cumulative learner attempts and accepts correct assisted answers without requiring paraphrasing. Evidence provenance still distinguishes assisted completion from independent work.

If a follow-up was saved before its answer stream could start, the interface retries the same reply ID rather than adding another reply. Failed or interrupted practice assessments show the saved submission and offer to restore it to the editor, including after reload and when earlier feedback exists. Learner answer line breaks are retained; selected display formulas keep display delimiters.
