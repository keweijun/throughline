# Does advance preparation reduce waiting? Three paired screening runs

Date: 2026-10-13 (user timezone). Isolated experiment only; production, authentication, and real-course progress were unchanged.

## CLI channel verification

CLI 0.162.0-alpha.17.2 used the configured custom Responses provider and Bearer authentication without requiring ChatGPT login. With the complete configuration, real READY requests succeeded for gpt-6.1-sol / medium and gpt-6-luna / medium.

The model directory returned codex-auto-review, gpt-5.5, gpt-5.6-luna, gpt-5.6-sol, gpt-5.6-terra, gpt-6-astra, gpt-6-luna, gpt-6-sol, gpt-6.1-sol, and gpt-reserve. Only the two requests above were tested; other entries were directory claims.

An initial preflight bypassed user configuration and its custom provider, so that failure did not apply to the configured channel. A handwritten directory probe initially omitted its Bearer field and returned 401; the corrected probe succeeded. No credentials/configuration changed or appear in this report.

## Controls

- Request gpt-6.1-sol / medium as in the learning chat. The provider implements backend identity; this experiment cannot independently authenticate routed model weights.
- A receives extracted original text and five PNG pages; B additionally receives concise preparation generated by the same provider/model and checked against pages. Both retain original access.
- Three sections cover conceptual application, derivation, and abstract concepts/calculation. Preset order: A/B, B/A, A/B. Fresh ephemeral CLI sessions, serial execution, no concurrent measured work.
- Retain the double-generation workflow: save the full lesson, then output it verbatim. Target 1600–2200 characters and two answer-free end questions. No simultaneous UI/model change.
- Use monotonic wall time from process start to completion and retain final agent_message events. Precise first-character timing is absent; completion is not TTFT. CLI and the long desktop chat differ, so direct comparison with its earlier 143 s is invalid.
- Configuration modification time stayed constant across six teacher runs. Record preparation costs separately from teacher-stage effects.

## Results

| Section | A: prepare live | B: prepared package | B relative to A | A/B characters | Separate preparation |
|---|---:|---:|---:|---:|---:|
| Photoelectric effect | 114.0 s | 131.6 s | 15.4% slower | 2197 / 2199 | 130.6 s |
| Bohr model | 175.8 s | 81.1 s | 53.9% faster | 2200 / 2191 | 135.8 s |
| Triangular wavefunction projection | 171.1 s | 145.1 s | 15.2% faster | 2199 / 2195 | 115.9 s |

All six saved texts match final output. Aggregate teacher time: A 461.0 s, B 357.7 s, a 22.4% reduction in this sample. Preparation adds 382.3 s; preparation+B totals 740.0 s, 60.5% above A. These are observed sums, not stable benefits or guarantees.

## Independent content review

Renamed all six outputs and hid conditions/times. An independent agent checked predefined requirements against 15 original images. All passed without key physics errors or obvious required-content reductions. One photoelectric example only converted kinetic energy to voltage, while its pair went from wavelength to stopping voltage. Both met minimum requirements but were not textually equivalent. Correctness/coverage review does not establish equal human learning outcomes.

## Conclusions supported

Preparation showed a foreground-wait benefit signal, especially for Bohr derivation, but not uniformly: photoelectric teaching was slower. One run per condition/section cannot exclude service variance, caching, or execution differences and does not establish significance or stable 22% acceleration.

Some runs used tools to check/adjust length and differed in script-save/edit steps. Identical length constraints do not eliminate this variation; ordinary teaching lacks such a precise character target, limiting generalization. Full text was still generated twice; removing that duplication was unmeasured here.

Preparation shifts work earlier rather than necessarily reducing computation. Real benefit requires testing overlap with reading/answering and lifecycle across user turns. No persistent pipeline or teaching workflow change was tested.
