# Course operations

Run `guided-learning --course <course-name> --request <request.json>`. Course names use lowercase letters, digits and hyphens (`quantum-v1`) and resolve inside the course library; `guided-learning courses` prints the library `root` and each course's `name`, `title`, source count and review backlog. `--workspace <directory>` addresses a course outside the library instead. The request file is UTF-8 JSON; omit `--request` to read JSON from stdin. Exit 0 returns `{ "ok": true, "result": ... }`; exit 1 returns `{ "ok": false, "error": { "code": ..., "message": ... } }`.

## Creating a course

Lead the intake: the learner knows what they want, you know what a good course from these materials needs. Every intake message offers concrete options drawn from the materials and marks one as **recommended**, so the learner can answer in a word or reply "ok" to accept every recommendation. Accept partial answers and fill the rest with your recommendations; "just build it" at any point means the same for everything not yet answered. Do not re-ask what the learner's request already said: list it as noted. Write in the learner's language.

When you have the `request_user_input` tool (Throughline Studio turns it on), ask every choice through it instead of in prose, so the learner clicks rather than types: one question per choice (goal, each prerequisite's level, depth, focus, how they like to learn, the route, where added files fit), up to the tool's limit per call, the recommended option first with "(recommended)" in its label, and short descriptions saying what each option changes. The learner can always answer in their own words with Other. Put the read-back and anything else the learner should read before choosing in your message first. Without the tool, ask in prose as below.

1. Get the learner's files and goal. If either is missing, explain in a few lines: attach the files or name their folder, and say what they want to learn; if they are unsure what to learn, suggest goals that fit the files. Attachments may arrive as local paths; if a file's content is visible but not its path, ask where it is saved, or ask the learner to put it in `<root>/<course-name>/inputs/`.
2. Read the files before asking anything, so every question and option is specific to them: what they cover, how they are organized, which exercises and solutions they hold, which prerequisites they assume, and which pages look scanned or unreadable. Propose a short course name and check it is not already listed by `guided-learning courses`.
3. Interview, in one message, always, even when the goal seems clear. Open with a read-back of the materials in a few lines (what they cover, their structure, exercises and solutions, pages that may need review) so the learner can correct a misreading. Then ask:
   - **Goal:** what they want to be able to do and by when, with options that fit the files (an exam on a date, solving the problem sets, a project, general understanding).
   - **Prior knowledge:** each prerequisite these materials actually assume, named specifically ("linear algebra: eigenvalues and diagonalization", not "maths"), rated none, some or solid.
   - **Depth:** overview (intuition and key results), standard (main derivations and worked examples) or rigorous (proofs, conditions and edge cases), recommending one from the goal and the materials.
   - **Focus:** parts of the materials to emphasize or skip, named from what you read ("lectures 1–2 look like review", "problem sets 4–6 have no solutions").
   - **How they like to learn:** a few contrasts that matter for this subject, such as intuition before formalism or the reverse, a worked example before each idea or after, short steps with frequent checks or longer stretches.
4. Offer a quick check when a prerequisite the route leans on is rated some or solid, or the learner is unsure of a level: a few short questions in one message on what the materials actually use from that topic, answered with a letter or a line. It calibrates the route; it is neither a lesson nor evidence. Reply with the right answer in a line each, propose a level and what it changes in the route ("I'll add a short section on diagonalization before chapter 2"), and use the level the learner agrees to. Skip the check when the learner declines or no answer could change the route.
5. Copy the learner's files into `<root>/<course-name>/inputs/`, keeping the originals. Sources are identified by absolute path, so register these stable copies, not files in Downloads or a temporary folder. Convert documents that are neither PDF nor text (below).
6. Run `course.init`, then `course.profile.save` (with a prerequisite's `check` when it was checked), then `preferences.save` with the teaching language when the learner writes in a supported language other than English, then `memory.save` and `memory.confirm` for each way they said they like to learn (below), then `widgets.save` with the add-ons this subject calls for (below), then `source.register` for each copy or conversion.
7. Propose the route before `curriculum.outline`: the chapters in a few lines, the first chapter's sections, and how they reflect the answers (foundation sections for prerequisites marked none that the goal needs, a later start for solid ones, exam topics first when there is a deadline). When the materials allow genuinely different routes, such as the lectures' own order or exam topics first, or a foundations chapter or prerequisites folded into the sections that need them, show each as an option with what it trades and recommend one. If the course uses add-ons, say in plain words what they will draw ("I'll graph the functions in chapters 2–4"), without naming add-ons or asking the learner to choose them. Also offer to build every chapter now or only the first, letting the app build the rest as they study. Once they agree, build without asking again.
8. Build the route chapter by chapter (see curriculum operations), then open the course with `guided-learning open <course-name>` as soon as the first chapter is built (see the [learning app](learning-app.md)) and build the rest unless the learner chose to let the app build them. Close with what was built, what still needs review and why, and two or three next steps that fit this course. Choose them from what you noticed in the materials, and let them show the range of what course work can do, not only housekeeping: adding the solutions to a problem set or reviewing flagged pages, but also filling in derivations the notes skip, adding programming exercises to a computational chapter, turning a past exam into practice in its style, adding a foundations section the learner may need, or making a cheat sheet. Never a generic list. In Studio, offer them as choices with `request_user_input` when you have it, and do the chosen one; elsewhere, give each as a `$throughline` request they can send.

## Converting documents

The app reads PDFs and text files: Markdown, plain text, LaTeX, code, CSV and any other file in UTF-8 or UTF-16 (a text file in another encoding is refused; re-encode the copy in `inputs/` as UTF-8). Convert every other document to PDF so the learner sees its layout beside the lesson: Word, PowerPoint, Excel, OpenDocument, RTF, Pages, Keynote and EPUB, which are refused when registered directly. Web pages are text, but their markup reads badly; convert them to PDF too.

1. Keep the original in `inputs/` and write the PDF to `inputs/converted/<original name>.pdf`.
2. Convert with whatever the learner already has: a document tool you find installed, Microsoft Office, LibreOffice (`soffice --headless --convert-to pdf`), Pages or Keynote, or Calibre for EPUB. Conversions usually need to run outside the sandbox. If nothing can convert, offer to install LibreOffice, which is free, or ask the learner to export a PDF themselves.
3. Check the PDF: as many pages or slides as the original, text that extracts, formulas and figures intact. Tell the learner what the conversion lost.
4. Register the PDF with `converted_from` set to the original.
5. When a slide deck has speaker notes, write them to `inputs/converted/<original name> (speaker notes).md`, a `## Slide N` heading followed by the notes for each slide that has any, and register it with the same `converted_from`. Read the notes with python-pptx, or from `ppt/notesSlides/*.xml` inside the `.pptx`. Cite the slide in the PDF and the explanation in the notes.

When the learner updates an original, or its hash no longer matches `converted_from.revision`, convert it again and register the conversions again.

## Requests

- `{"op":"course.init","title":"Quantum"}` creates a course; reopening via init preserves the existing title and state.
- `{"op":"course.status"}` returns `course`, `position`, `sources` and `profile`.
- `{"op":"course.profile.save","profile":{"goal":"Pass the final on 15 Jan","depth":"standard","prerequisites":[{"topic":"Complex numbers","level":"solid"},{"topic":"Fourier transforms","level":"none"}],"focus":"Exam-style problems"}}` saves the learner profile from the interview, replacing any earlier one. `depth` is `overview`, `standard` or `rigorous`; levels are `none`, `some` or `solid`; `focus` and `notes` are optional. The app's teacher reads it for every lesson. It records what the learner reported, never mastery. A prerequisite may carry `check`: what a quick check in the interview showed (`{"topic":"Eigenvalues","level":"some","check":"Found the eigenvalues of a 2x2 matrix; unsure how to diagonalize"}`). Save again when the learner changes their mind.
- `{"op":"memory.save","id":"intake-1","kind":"preference","text":"Worked example before each new idea"}` then `{"op":"memory.confirm","id":"intake-1"}` records a way the learner said they like to learn as a confirmed preference in the course memory, which the app's teacher follows and the learner can edit or delete in the app. Write it as a short instruction about teaching, one per entry, and only what the learner chose. Course-wide preferences omit `concept_id`.
- `{"op":"preferences.save","language":"zh-CN"}` sets the course's teaching language: `en` (default) or `zh-CN`. The app teaches new lessons, answers, exercises and preparation in it; the learner can change it in Settings. `preferences.view` reads it; `preferences.save` changes only the fields it is given.
- `{"op":"widgets.list"}` returns the add-on `library` (`id`, `summary`, `subjects`) and the course's `selected` ids. Lessons always have the basic widgets: LaTeX, highlighted code, callouts and Mermaid diagrams. `{"op":"widgets.save","ids":["plot"]}` replaces the course's add-ons; pick those the materials will use (`plot` for courses that study functions and their graphs, `chemistry` for chemical formulas and equations), none when none fits. The app's teacher learns to use only the selected ones; lessons already written with an add-on still render after it is removed. The learner never manages add-ons: when they ask for more or fewer drawings of a kind an add-on provides, change the selection; for drawings no add-on provides, say the app cannot draw them yet. An unknown id is rejected with `unknown_widget`.
- `{"op":"source.register","path":"/absolute/path/slides.pdf"}` returns `source` containing stable `id`, normalized `path`, SHA256 `revision`, `status`, `verification`, and `errors`. Repeat after a file changes. Missing files stay visible with a failed latest registration; an earlier revision remains readable. A successful registration means the attempt was recorded, not necessarily that extraction succeeded. For a file converted from another document, add `"converted_from":"/absolute/path/lecture.pptx"`: the source then carries `converted_from` with the original's `path` and the SHA256 `revision` that was converted, and the app names the original. Registering again without the field keeps it; an unreadable original is rejected with `invalid_request`.
- `{"op":"source.read","source_id":"src-..."}` returns the latest available snapshot with `units`, `status`, `errors`, and `verification`; pass `revision` to retrieve a previous snapshot. Each unit has stable within-revision `id`, `locator` and `text`. Text files use `{ "line": 1 }`, PDF uses `{ "page": 1 }`. PDF empty/image-only pages are `needs_review`.
- `{"op":"position.save","request_id":"checkpoint-1","position":{"goal":"Understand normalization","progress":"Introduced probability density","next_step":"Normalize the example"}}` saves a minimal mainline position object.
- `{"op":"annotations.list","concept_id":"optional-section"}` returns the learner's `annotations` (highlights, notes and bookmarks), oldest first. They are private to the learner: read them only when the learner asks about their own notes, never as teaching context or evidence (ADR 0005). `annotations.save` (`id`, `kind`, and `passage` (with `occurrence`, which repeat of it in its text, 0 for the first), `note` and one of `turn_id` (lesson or side-question answer), `task_id` (exercise), `source` or `concept_id`; an existing `id` only updates `note`) and `annotations.delete` (`id`) exist for the app; change annotations only when the learner asks.

`verification: pending` means formulas, images and page mapping have not been independently checked. Source units are extraction units, not a completed coverage ledger. A text line must not be presented as a PDF page.

## Storage and extension contract

The workspace contains `course.sqlite3` and `sources/<source-id>/<sha256>` byte snapshots. Use operations instead of editing the database. Source identity follows normalized absolute path; moving a source registers a new identity. Keep a stable input location for revisions.

Python callers use `guided_learning.execute(workspace, request)`; validation errors raise `OperationError` with `.code`. Each request holds one SQLite transaction: `BEGIN IMMEDIATE` for a write, a deferred read-only one for operations listed in `guided_learning.api.READS`. An exception rolls it back. Operation modules export `OPERATIONS = {"operation.name": handler}`; add the module name to `guided_learning.api.MODULES`. Handlers take `(store, request)` and return JSON-serializable results. `store.get(namespace, key, default=None)`, `put(namespace, key, value)`, `list(namespace)` and `delete(namespace, key)` read/write JSON documents; reserve a separate namespace for each feature. `store.db` is available when relational constraints are needed. Handlers must not commit or close the shared transaction.

Core namespaces: `course` (`metadata`, `position`, `schema`: the course format version, which operations migrate forward and never write by hand), `sources` (key: source ID), `source_revisions` (key: `<source-id>:<revision>`). Preserve old snapshots and user learning evidence when building on source changes. Reading a snapshot may use a cached earlier revision even when the newest registration failed; consult source status as well.

Checkpoint writes (`position.save` and `mainline.enter`) require a unique nonempty `request_id` for each intended change. Reuse the same ID only for an identical retry. A retry returns `replayed:true`, the **current** `position`, and the first response under `original_result`; it never restores that old position. Changed contents under an existing ID are rejected. Use `session.resume` for current due items after a replay. Existing databases remain readable; update older calling scripts to supply IDs.
